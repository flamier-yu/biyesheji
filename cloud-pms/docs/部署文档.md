# 云协同 PMS 部署文档

本文档覆盖 **本地开发环境搭建**、**生产环境部署（Docker Compose）** 与 **常见问题排查**。

---

## 一、环境要求

| 组件 | 版本要求 | 说明 |
|---|---|---|
| JDK | 1.8 及以上 | 后端编译运行环境（推荐 1.8.0_461 或以上） |
| Maven | 3.6+ | 后端构建工具 |
| Node.js | 18+ | 前端构建（推荐 20 / 22 LTS） |
| MySQL | 8.0+ | 主数据库，需支持 `utf8mb4` |
| Redis | 3.0+ | 缓存与令牌存储（3.0 亦可用，客户端已使用 Jedis 兼容） |
| Nginx | 1.20+ | 生产环境反向代理（可选，本地开发不需要） |
| Docker | 20.10+ | 容器化部署（可选） |

**硬件建议**：开发机 8G 内存起步；生产单机部署建议 4 核 8G。

## 二、本地开发环境搭建

### 2.1 准备数据库

```bash
# 1. 创建数据库（注意字符集）
mysql -uroot -p -e "create database biyesheji default character set utf8mb4 collate utf8mb4_general_ci;"

# 2. 按顺序导入三个脚本（顺序不能颠倒）
mysql -uroot -p --default-character-set=utf8mb4 biyesheji < sql/01-schema.sql
mysql -uroot -p --default-character-set=utf8mb4 biyesheji < sql/02-data.sql
mysql -uroot -p --default-character-set=utf8mb4 biyesheji < sql/03-business-menu.sql

# 3. 验证（应看到 23 张表）
mysql -uroot -p -e "use biyesheji; show tables;"
```

> ⚠️ **必须加 `--default-character-set=utf8mb4`**，否则中文数据会乱码。

#### 用图形客户端（Workbench / Navicat）导入时的问题

**症状**：

```
Error Code: 1175. You are using safe update mode and you tried to update
a table without a WHERE that uses a KEY column.
```

**原因**：`02-data.sql` 含大量 `DELETE FROM xxx;`（清空表后重新插入），
而 MySQL Workbench 默认开启「安全更新模式」（Safe Updates），
会拒绝执行不带 WHERE 或 WHERE 未使用索引列的 `UPDATE`/`DELETE`。

**本项目的处理**：`02-data.sql` 和 `03-business-menu.sql` 开头已内置

```sql
SET SQL_SAFE_UPDATES = 0;   -- 临时关闭（仅当前会话）
...
SET SQL_SAFE_UPDATES = 1;   -- 执行完恢复
```

所以**直接在 Workbench 里执行即可，无需改任何设置**。

若仍报同样的错，按以下顺序排查：

| 排查项 | 做法 |
|---|---|
| 客户端未重连 | 脚本里的 `SET` 只对当前连接生效。执行前先重新连接一次数据库 |
| 只选中了部分语句执行 | Workbench 里用「执行整个脚本」(闪电图标带光标) 而不是「执行当前语句」，否则会漏掉开头的 `SET` |
| 客户端版本差异 | 备选方案：执行前手动加一行 `SET SQL_SAFE_UPDATES = 0;` |
| 不想动 SQL | 关掉客户端限制：Workbench → Edit → Preferences → SQL Editor → 取消 *Safe Updates* → **重连数据库生效** |

> 最省事的替代方式：用命令行执行，命令行默认不受 Safe Updates 限制：
> ```bash
> mysql -uroot -p --default-character-set=utf8mb4 biyesheji < sql/02-data.sql
> ```

### 2.4 启动后端

```bash
cd pms-server
mvn clean package -DskipTests

# 启动（注意：必须显式指定端口）
java -jar target/pms-server.jar --server.port=8080
```

**⚠️ 为什么必须写 `--server.port=8080`？**
某些 CI/沙箱环境会注入 `SERVER_PORT` 环境变量，若不显式指定，应用可能绑定到意料之外的端口（甚至因端口被占用而启动失败）。显式指定命令行参数优先级最高，可避免这类问题。


## 三、生产环境部署（混合模式）

### 3.0 部署拓扑说明

本项目采用**混合部署**：数据库独立部署（便于专职运维与备份），其余服务容器化。

| 组件 | 部署方式 | 原因 |
|---|---|---|
| **MySQL** | **宿主机或独立服务器**（不由编排创建） | 数据安全边界清晰、便于单独备份与迁移、可用现成实例 |
| **Redis** | 容器 | 只存缓存与令牌，无持久化数据风险 |
| **后端应用** | 容器 | 环境一致、便于滚动发布 |
| **前端 Nginx** | 容器 | 托管静态资源 + 反向代理 |

> 如需**全容器化**（数据库也在 Docker 里，适合本地演示），可从 Git 历史取回旧版 `docker-compose.yml`，或把 `services.mysql` 段按下方模板加回：
> ```yaml
>   mysql:
>     image: mysql:8.0
>     container_name: pms-mysql
>     environment:
>       MYSQL_ROOT_PASSWORD: root
>       MYSQL_DATABASE: biyesheji
>     volumes:
>       - mysql-data:/var/lib/mysql
>       - ./sql:/docker-entrypoint-initdb.d:ro
> ```

### 3.1 第一步：准备外部 MySQL

**① 建库并导入数据**

```bash
mysql -uroot -p -e "create database biyesheji default character set utf8mb4 collate utf8mb4_general_ci;"
mysql -uroot -p --default-character-set=utf8mb4 biyesheji < sql/01-schema.sql
mysql -uroot -p --default-character-set=utf8mb4 biyesheji < sql/02-data.sql
mysql -uroot -p --default-character-set=utf8mb4 biyesheji < sql/03-business-menu.sql
```

**② 给应用账号授权远程访问**

```bash
mysql -uroot -p < deploy/init-external-db.sql
```

该脚本会创建专用账号 `pms`（而不是直接用 root）并只授予 `biyesheji` 库的权限。

**③ 检查两处系统配置（最容易漏）**

| 检查项 | 说明 |
|---|---|
| `bind-address` | 若为 `127.0.0.1`，外部连不上。执行 `SHOW VARIABLES LIKE 'bind_address';` 确认，需改为 `0.0.0.0` |
| 防火墙 / 安全组 | MySQL 与 Docker 不同机时需放行 3306 端口 |

```sql
-- 验证授权结果
SELECT User, Host FROM mysql.user WHERE User = 'pms';
SHOW GRANTS FOR 'pms'@'%';
```

### 3.2 第二步：配置 .env

```bash
cp .env.example .env
vi .env
```

**关键：`DB_HOST` 怎么填**

| MySQL 位置 | `DB_HOST` 填什么 |
|---|---|
| **与 Docker 同一台机器** | `host.docker.internal` ← 推荐 |
| 局域网另一台服务器 | 该机器的内网 IP，如 `192.168.1.20` |
| 云端 RDS | RDS 提供的内网/外网地址 |

> **为什么同机也要用 `host.docker.internal` 而不是 `127.0.0.1`？**
> 容器内的 `127.0.0.1` 指的是**容器自己**，不是宿主机。`host.docker.internal` 是 Docker 提供的特殊域名，解析到宿主机网关地址。
> Docker Desktop（Windows/Mac）原生支持；Linux 需要 Docker 20.10+ 并在编排里声明 `extra_hosts: - "host.docker.internal:host-gateway"` —— **本项目已配好**。

### 3.3 第三步：构建并启动

```bash
# 构建后端产物
cd pms-server && mvn clean package -DskipTests && cd ..

# 构建前端产物
cd pms-web && npm install && npm run build && cd ..

# 启动
docker compose up -d
docker compose ps
docker compose logs -f backend
```

看到如下日志即为成功：

```
Tomcat started on port(s): 8080 (http)
云协同 PMS 启动成功！
```

访问 `http://<服务器IP>`（默认 80 端口）。

### 3.4 连通性排查

混合部署最常见的卡点是「容器连不上宿主机数据库」，按顺序排查：

```bash
# ① 容器内能否解析宿主主机名
docker compose exec backend ping -c 2 host.docker.internal

# ② 容器内能否连通 3306 端口
docker compose exec backend sh -c "nc -zv host.docker.internal 3306 || telnet host.docker.internal 3306"

# ③ 用应用账号从容器内直连测试（排除口令与授权问题）
docker compose exec backend sh -c "mysql -h host.docker.internal -u pms -p'Pms@2026' -e 'SELECT 1;'"

# ④ 查看后端启动日志中的具体报错
docker compose logs backend | grep -i -E "error|exception|denied|refused"
```

| 报错关键字 | 含义 | 解决 |
|---|---|---|
| `Connection refused` | 端口不通 | 检查 MySQL 是否启动、bind-address、防火墙 |
| `Access denied for user` | 账号或密码不对 | 核对 `.env`；确认授权脚本已执行 |
| `Unknown database` | 库不存在 | 执行建库语句 |
| `Communications link failure` | 网络层不通 | 检查 `DB_HOST` 填写是否正确（同机是否写成 127.0.0.1） |
| `Public Key Retrieval is not allowed` | MySQL 8 认证插件问题 | 确认 JDBC URL 带了 `allowPublicKeyRetrieval=true`（模板已包含） |

### 3.5 非 Docker 部署（完全不用容器）

若目标机器没有 Docker，可全手工部署：

**后端**（Linux）：

```bash
nohup java -Xms256m -Xmx512m -DLOG_HOME=/opt/pms/logs \
  -jar /opt/pms/pms-server.jar --server.port=8080 \
  > /opt/pms/logs/startup.log 2>&1 &
```

**前端 + Nginx**：

```bash
# 将 dist 放到 Nginx 站点目录
cp -r pms-web/dist/* /usr/share/nginx/html/

# 使用项目提供的配置
cp deploy/nginx.conf /etc/nginx/conf.d/pms.conf
nginx -t && nginx -s reload
```

### 3.6 关键配置项（生产必改）

| 配置 | 位置 | 说明 |
|---|---|---|
| `PMS_JWT_SECRET` | 环境变量 / `application.yml` | **必须修改**，建议 32 位以上随机字符串 |
| 数据库密码 | `application-dev.yml` | 不要用 root/root |

## 四、常见问题排查

### 4.1 启动失败类

| 现象 | 原因 | 解决 |
|---|---|---|
| `Port 8080 was already in use` | 端口被占用 | 换端口 `--server.port=8081`，或查杀占用进程 |
| 端口跑到意料之外的端口 | 环境注入了 `SERVER_PORT` | 显式加 `--server.port=8080` |
| `Access denied for user` | 数据库账号密码不对 | 检查 `application-dev.yml` |
| `Unknown database 'biyesheji'` | 没建库 | 执行建库语句 |
| 启动卡在 HikariPool | 数据库连不上 | 检查网络、防火墙、账号权限 |
| `Communications link failure` | MySQL 未启动或时区配置问题 | 确认服务在跑，URL 加 `serverTimezone=Asia/Shanghai` |

### 4.2 功能异常类

| 现象 | 原因 | 解决 |
|---|---|---|
| 中文乱码 | 导入 SQL 未指定字符集 | 加 `--default-character-set=utf8mb4` 重新导入 |
| **Error Code: 1175** 安全更新模式 | 客户端（Workbench 等）拦截无 WHERE 的 DELETE | 脚本已内置开关；若仍报错，看 2.1 节的排查表 |
| 登录一直提示「账号或密码错误」 | ① 密码不对 ② 数据库里密码字段为空 ③ 表里有非表字段未标注 | 用 `PasswordGenerator` 重新生成密文；检查实体是否有 `@TableField(exist = false)` 遗漏 |
| 登录提示验证码错误 | 验证码已过期（2 分钟） | 刷新验证码；或临时关闭 `pms.captcha-enabled` |
| 接口返回 401 | 令牌过期或未携带 | 重新登录；检查请求头 `Authorization: Bearer <token>` |
| 接口返回 403 | 当前角色无该权限 | 到「角色管理」为角色勾选对应菜单权限 |
| 页面菜单不显示 | 角色未授权该菜单 | 角色管理中重新分配；或该目录下没有子菜单（前端会过滤空目录） |
| 访问根路径跳到 404 | 动态路由未补根路径规则 | 确认 `router/index.js` 中有 `path: '/'` 的重定向 |
| 侧边栏/顶栏显示两遍 | 路由 Layout 嵌套 | 检查 `buildRoutes` 是否只对顶层菜单包 Layout |

### 4.3 前端类

| 现象 | 原因 | 解决 |
|---|---|---|
| 端口从 5173 变成 5174 | 有僵尸 vite 进程占着 5173 | 清理残留 node 进程后重启 |
| 请求 404 / 跨域 | 代理未生效或后端未启动 | 检查 `vite.config.js` 的 `/dev-api` 代理与后端状态 |
| 页面空白 | 动态路由未注册成功 | 看浏览器控制台，检查 `/getRouters` 是否返回 200 |
| npm install 极慢 | 未配置国内镜像 | `npm config set registry https://registry.npmmirror.com` |

### 4.4 Maven 类

| 现象 | 原因 | 解决 |
|---|---|---|
| 依赖下载极慢/卡住 | 走默认中央仓库 | 在 `~/.m2/settings.xml` 配置阿里云镜像 |
| `mysql-connector-java version is missing` | Spring Boot 2.7.18 已改用新坐标 | 用 `com.mysql:mysql-connector-j` |
| 编译报「找不到符号」 | 依赖未引入完全 | 核对 `pom.xml`，尤其 `spring-boot-starter-websocket` |

## 五、日常运维

### 5.1 日志

| 文件 | 内容 |
|---|---|
| `logs/pms-server.log` | 全量日志，按天 + 50MB 滚动，保留 30 天 |
| `logs/pms-server-error.log` | 仅 ERROR 级别 |

日志路径通过启动参数控制：`-DLOG_HOME=/your/path`

### 5.2 数据备份与恢复

#### 5.2.1 核心原则：用逻辑备份，不要复制数据文件

| 方式 | 做法 | 结论 |
|---|---|---|
| **逻辑备份**（推荐） | `mysqldump` 导出 SQL 文本 | 跨版本、跨平台、可读、导入报错易发现 |
| 物理复制（不推荐） | 直接拷贝 `/var/lib/mysql` 数据目录 | 版本绑定、必须冷停机、失败难察觉 |

**为什么不能直接复制数据文件？**

MySQL 的 InnoDB 数据文件（`ibdata`、`.ibd`）**不是自包含的**，它依赖：

- **MySQL 版本必须完全一致**（8.0.x 与 5.7 的物理格式不兼容）
- `innodb_page_size` 必须一致（默认 16KB，改过就废）
- 复制时**数据库必须已完全停止**，热复制会得到损坏文件
- 文件属主是容器内的 mysql 用户（uid 999），换环境要重设权限

> 物理复制只在**同机器整机灾备**或**大库快速重建**时才考虑。
> 日常备份、换服务器、交付客户，一律用逻辑备份。

#### 5.2.2 一键备份

项目提供了 `deploy/backup.sh`（Docker 与宿主机两种模式都支持）：

```bash
chmod +x deploy/backup.sh

# Docker 模式（默认，备份 compose 里的 mysql 容器）
./deploy/backup.sh

# 宿主机模式
DB_MODE=host DB_HOST=127.0.0.1 ./deploy/backup.sh
```

脚本会依次完成：**一致性快照导出 → 校验（表数/非空）→ gzip 压缩 → 清理超期备份**，并在失败时删除半成品文件。

备份产物：`backups/biyesheji_20260915_020000.sql.gz`

#### 5.2.3 配置定时任务

```bash
crontab -e

# 每天凌晨 2 点备份，日志单独记录
0 2 * * * /opt/cloud-pms/deploy/backup.sh >> /var/log/pms-backup.log 2>&1
```

建议保留策略：**本地保留 7 天 + 异地/对象存储保留 30 天**。

```bash
# 备份完成后同步到对象存储（示例）
0 3 * * * aws s3 sync /opt/cloud-pms/backups s3://my-bucket/pms-backups/
```

> ⚠️ **备份文件必须异地存放**。机器挂了而备份还在同一块盘上，等于没有备份。

#### 5.2.4 恢复

```bash
chmod +x deploy/restore.sh

# 会先打印确认信息，输入 yes 才执行
./deploy/restore.sh backups/biyesheji_20260915_020000.sql.gz
```

恢复前请务必确认：

1. **确认要覆盖的目标库**（脚本会先 `DROP DATABASE` 再重建）
2. 恢复完成后**重启后端服务**，清理连接池中的旧连接
3. 如果库里存的是 BCrypt 密码，恢复后原有登录态（Redis 中的令牌）也需清理

#### 5.2.5 三种迁移场景怎么做

| 场景 | 做法 |
|---|---|
| **换服务器 / 迁移到云** | 老机器 `backup.sh` 导出 → 传到新机器 → `restore.sh` 导入。**跨版本、跨平台都可行** |
| **交付给客户** | 直接把项目 `sql/` 目录下的三个脚本给对方（`01-schema` + `02-data` + `03-business-menu`），比给备份文件更干净 |
| **整机灾备（同环境快速恢复）** | 才考虑物理复制：`docker compose stop mysql` → 复制 `mysql-data` 卷 → 新机器挂载 → 启动 |

#### 5.2.6 备份有效性验证

**没有验证过的备份等于没有备份。** 建议每月做一次恢复演练：

```bash
# 1. 恢复到一个临时库（不要覆盖生产库）
docker exec -i pms-mysql mysql -uroot -proot \
  -e "CREATE DATABASE biyesheji_verify DEFAULT CHARACTER SET utf8mb4;"
gunzip -c backups/latest.sql.gz | docker exec -i pms-mysql mysql -uroot -proot biyesheji_verify

# 2. 核对关键表的记录数
docker exec -i pms-mysql mysql -uroot -proot -e "
  SELECT 'sys_user' t, COUNT(*) c FROM biyesheji_verify.sys_user
  UNION ALL SELECT 'sys_menu', COUNT(*) FROM biyesheji_verify.sys_menu
  UNION ALL SELECT 'pm_task', COUNT(*) FROM biyesheji_verify.pm_task;
"

# 3. 确认无误后删掉临时库
docker exec -i pms-mysql mysql -uroot -proot -e "DROP DATABASE biyesheji_verify;"
```

#### 5.2.7 Redis 要不要备份

**基本不需要。** 本项目 Redis 里存的是：

| 内容 | 丢失影响 |
|---|---|
| 登录令牌（`pms:login:user:*`） | 用户需重新登录，无数据损失 |
| 图形验证码（`pms:captcha:*`） | 2 分钟后自动过期，无影响 |
| 参数缓存（`pms:config:*`） | 会自动从数据库重新加载 |

**唯一例外**：如果你的业务扩展到把重要数据放 Redis（如排行榜、消息队列），才需要开启 RDB/AOF 持久化并纳入备份范围。

### 5.3 定时任务

系统内置三个定时任务（`ScheduledTasks`），无需额外配置：

| 时间 | 任务 |
|---|---|
| 每日 01:00 | 为进行中的项目生成燃尽图快照 |
| 每日 09:00 | 扫描逾期任务，推送预警消息 |
| 每日 09:05 | 扫描即将到期任务（提前 1 天提醒） |
