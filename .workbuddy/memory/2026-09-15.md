## Bug 修复：侧边栏与顶栏重复渲染两遍

**现象**：登录后所有页面左侧菜单栏和顶部栏都渲染了两遍（Layout 嵌套）。

**根因**：`pms-web/src/router/index.js` 的 `buildRoutes()` 缺少"层级"判断。

后端 `/getRouters` 返回的菜单里，目录的 `component` 是 `"Layout"`，子菜单的 `component` 才是具体页面（如 `system/user/index`）。
原实现对所有非 Layout 的菜单统一走"包一层 Layout"分支，导致**子菜单也被包了 Layout**，最终结构变成：

```
Layout  →  Layout  →  页面      ← 双层布局，侧边栏+顶栏渲染两次
```

**修复**：给 `buildRoutes` 增加 `isTop` 参数，只有**顶层**非 Layout 的叶子菜单才包一层布局，子菜单（`isTop === false`）直接挂页面组件：

```js
function buildRoutes(menus, isTop = true) {
  menus.forEach((menu) => {
    const children = buildRoutes(menu.children || [], false)
    if (menu.component === 'Layout') {
      // 目录：用 Layout 承载子菜单
    } else if (isTop) {
      // 顶层叶子菜单：包一层 Layout（children 内层 path 为空）
    } else {
      // 子菜单：直接指向页面组件，不再包 Layout ✅
    }
  })
}
```

**验证方式**（未下载 Chromium，改用结构校验）：
写了临时 `verify-routes.mjs`，用真实后端菜单数据跑同一份转换逻辑并断言：
- Layout 节点数 = 4（恰好等于顶层路由数，无嵌套）
- 页面组件数 = 10
- 断言「不存在 Layout 嵌套」通过，exit 0

**经验（复用时注意）**：动态路由场景下，判断"是否包布局"必须看**层级**而不是只看 component 类型。只要子菜单也参与"包 Layout"逻辑，就必然出现双层布局。验证过即可删除临时脚本，保持项目干净。

## Bug 修复：访问根路径落到 404

**现象**：已登录状态下访问 `http://localhost:5173/#/`，会跳到 `/404` 页面。

**根因**：动态路由方案下，**后端菜单里没有 `/` 这个路径**（菜单是 `/dashboard`、`/system`、`/project`、`/report`、`/message`）。
链路：有 token → 守卫加载动态路由 → `next({ ...to })` 重新导航到 `/` → 无路由可匹配 → 命中兜底通配 `/:pathMatch(.*)*` → 重定向 `/404`。

连带问题：已登录时手动访问 `/login`，守卫 `next('/')` 也会同样落到 404。

**区分两种情况**（这是排查时的关键）：
- 未登录访问 `/` → 守卫已正确跳登录页 ✅
- 已登录访问 `/` → 落到 404 ❌（缺根路径规则）

**修复**（只改 `src/router/index.js`）：
1. 新增 `findFirstLeafPath(routes)` —— 递归从路由表里找第一个非 hidden 的可访问叶子路径，遇到只有空 path 子路由的（如 `/dashboard` 那种外层 Layout 包裹）则回退用自身 path
2. 动态路由注册后补一条 `router.addRoute({ path: '/', redirect: homePath })`，`homePath || '/dashboard'` 兜底

**验证方式**（临时 node 脚本，跑完即删）：用三组菜单数据跑同一份逻辑并断言
- 管理员（首个菜单是工作台）→ `/dashboard`
- 无工作台权限的角色（首个是目录 `/project`）→ `/project/list`（正确下钻到子菜单）
- 空菜单 → 回退 `/dashboard`
三组全部通过，exit 0

**经验**：动态路由方案里，**必须显式补根路径规则**。后端菜单只描述"有哪些页面"，不描述"从哪进"，`/` 的入口语义要靠前端自己定义，否则必然落空到兜底 404。

**顺带清理**：发现两个 vite 进程（旧的 PID 7632 仍占着 5173 但不服务，新的被挤到 5174）。按命令行含 `pms-web` + `vite` 精确匹配杀掉残留进程，重启后 5173 单进程正常。

**排查这类"端口不对"问题的技巧**：前端端口突然从 5173 变 5174，说明有僵尸进程占着 5173，用 `Get-NetTCPConnection -LocalPort 5173` 找 owner PID 再核对命令行清理。

## Docker 部署答疑 + 备份方案

小宇以前是「前后端分别部署 + Nginx 反代」，对全容器化方式有疑问，核心关切是**数据安全**。

### 已确认的部署结构

`docker-compose.yml` 里 **MySQL 和 Redis 也在 Docker 内**，共四个容器：`pms-mysql` / `pms-redis` / `pms-backend` / `pms-frontend`。

容器间靠**服务名**互访（`jdbc:mysql://mysql:3306/...`、`SPRING_REDIS_HOST: redis`），不走 localhost —— compose 会建内部网络，服务名即容器主机名。宿主机调试用 Navicat 可连映射出来的 `localhost:3306`。

### 四种部署模式对比（重要认知）

| 模式 | 数据库位置 | 适合场景 |
|---|---|---|
| 全容器化（本项目配置） | 容器内 | 开发、演示、单机小规模 |
| 混合部署（生产主流） | 云 RDS / 独立服务器 | 正式生产，应用容器化滚动发布 |
| 全宿主机（小宇以前的习惯） | 宿主机安装 | 传统运维 |

### 备份方案（新增 `deploy/backup.sh` + `deploy/restore.sh`）

**核心原则：用逻辑备份，不要复制数据文件。**

| 方式 | 适用 | 限制 |
|---|---|---|
| **逻辑备份**（mysqldump）✅ | 日常备份、迁移、交付 | 无版本限制，跨平台 |
| 物理复制（拷 `/var/lib/mysql`）❌ | 仅同机器整机灾备 | 版本必须完全一致、`innodb_page_size` 需一致、必须冷停机、权限需重设、失败难察觉 |

**backup.sh 要点**：
- 关键参数 `--single-transaction`（一致性快照不锁表）、`--routines --triggers --events`、`--set-gtid-purged=OFF`、`--hex-blob`、`--default-character-set=utf8mb4`
- **备份后校验**：文件非空 + 含 `CREATE TABLE`，不满足则删除半成品并报错
- gzip 压缩 + 按天数清理超期备份
- 支持 `DB_MODE=container|host` 两种模式

**restore.sh 要点**：二次确认（输入 yes）→ 解压到临时文件 → DROP + CREATE DATABASE → 导入 → 校验表数与源文件是否一致。

**实测验证**（PowerShell 直调 mysqldump，因本机 Git Bash 损坏）：导出 62 KB，`CREATE TABLE` 23 个（与库内表数一致），中文无乱码，压缩后 11.1 KB（约 5.6:1）。

### 踩坑提醒（写进部署文档 5.2 节）

1. **`docker compose down -v` 会清空数据卷**，不加 `-v` 则数据保留
2. **`sql/` 目录只在数据卷为空时执行一次**（MySQL 镜像行为），改脚本要手动导入或 `down -v` 重置
3. **宿主机已装 MySQL 会与 `3306:3306` 冲突**，改端口或删掉 DB 的 ports 映射（同网络内不需要暴露）
4. **命名卷不在项目目录下**，想直接看文件要改成绑定挂载 `./data/mysql:/var/lib/mysql`
5. **备份必须异地存放**，且要定期做恢复演练（没验证过的备份等于没有备份）
6. **Redis 基本不需要备份** —— 本项目 Redis 只存令牌/验证码/参数缓存，丢了重新登录即可

**生产环境建议**：把 MySQL 拆出去（RDS 或独立机器），`docker-compose.yml` 删掉 mysql 服务，数据源指向真实地址；同时删掉 DB 的 ports 映射减少攻击面。

## 部署方案改造：全容器化 → 混合模式

小宇明确了他的部署思路：**MySQL 本地/独立部署（提供地址账号密码库名），Redis 用 Docker 起**。已按此改造。

### 改造后的编排（`docker-compose.yml`）

| 服务 | 部署方式 | 说明 |
|---|---|---|
| MySQL | **外部**（不由编排创建） | 数据边界清晰、便于专职备份 |
| redis | 容器 | `redis:7-alpine` + AOF，端口仅监听 `127.0.0.1` |
| backend | 容器 | 数据源由 `.env` 变量注入 |
| frontend | 容器 | nginx:1.24-alpine |

**已移除**：`mysql` 服务、`mysql-data` 卷。

### 关键技术点：容器如何访问宿主机 MySQL

**容器内的 `127.0.0.1` 指容器自己，不是宿主机** —— 这是混合部署最大的坑。

解法：编排中声明
```yaml
extra_hosts:
  - "host.docker.internal:host-gateway"
```
Docker Desktop（Win/Mac）原生支持；Linux 需 Docker 20.10+ 并显式声明 `host-gateway`（已配好，跨平台通用）。

`.env` 中 `DB_HOST` 取值规则：
- MySQL 与 Docker 同机 → `host.docker.internal`
- 异机 → 对方内网 IP
- 云 RDS → RDS 地址

## Bug 修复：Workbench 导入 02-data.sql 报 Error Code 1175

**现象**：小宇用 MySQL Workbench 执行 `02-data.sql`，在 `DELETE FROM sys_dept;` 处报错：
```
Error Code: 1175. You are using safe update mode and you tried to update a table
without a WHERE that uses a KEY column.
```

**根因**：MySQL Workbench 默认开启 **Safe Updates**，拒绝执行不带 WHERE（或 WHERE 未用索引列）的 `UPDATE`/`DELETE`。

统计受影响语句：
- `01-schema.sql`：**无**（只有 DROP/CREATE，不受此限制）
- `02-data.sql`：**21 处** `DELETE FROM xxx;`（清空重插模式，全无 WHERE）
- `03-business-menu.sql`：`DELETE FROM sys_role_menu WHERE menu_id BETWEEN ...` —— `menu_id` 在 `sys_role_menu` 里是联合主键的一部分但**不是独立索引列**，同样会被拦

**修复方案（改 SQL 文件而非让用户改客户端设置，最彻底）**：
在 `02`/`03` 开头加 `SET SQL_SAFE_UPDATES = 0;`，末尾加 `SET SQL_SAFE_UPDATES = 1;` 恢复，并写明原因注释。

**验证方法（关键技巧）**：命令行 mysql 默认 `SQL_SAFE_UPDATES=0`，直接跑**暴露不出问题**。必须用 `--init-command` 先开启来模拟 Workbench 行为：
```bash
mysql -uroot --init-command="SET SQL_SAFE_UPDATES=1" -D biyesheji -e "source xxx.sql"
```
实测两个脚本均无报错，数据校验通过（sys_menu=80、role_menu 1→80/2→38/3→15）。

**文档同步**：部署文档 2.1 节新增「图形客户端导入问题」小节（症状/原因/排查表/命令行替代方案），4.2 节问题表加一行 1175；README 3.2 节加提示。

**经验**：**初始化脚本应自带环境适配**，不要假设用户会改客户端设置。`SET SQL_SAFE_UPDATES` 这类会话级开关写在脚本里，用 Workbench / Navicat / 命令行执行都不会有差异 —— 这对交付给学生尤其重要，他们多半不知道去哪关 Safe Updates。
